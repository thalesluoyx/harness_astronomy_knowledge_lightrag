**文档状态**：已归档

## 一、 方案审核结论

经过对架构决策记录（ADR-01）的审核及对 2026 年最新 RAG（检索增强生成）技术生态的评估，确认**采用 LightRAG 构建天文学知识库是当前受限环境下的最优方案，完全可行。**

### 1. 核心优势印证
* **完美契合增量更新需求**：与微软 GraphRAG 牵一发而动全身的全图重算机制不同，LightRAG 采用追加合并式（Union）更新机制。新引入的书籍能够平滑融入现有图谱，极大地节省了算力成本与时间。
* **均衡的宏观与微观挖掘能力**：其独创的双层检索架构能够同时满足跨越 150 本书的全局宏观趋势提炼（C型问题）和细微逻辑链条追踪（D型问题）。
* **符合 2026 行业趋势**：在最新的生产实践中，LightRAG 被公认为动态更新和低预算场景下的标准答案，其首次建库（约占 MiniMax 6 亿月度配额的 17%）和后续增量更新（约 200 万 Token）成本均在高度可控的安全线内。

## 二、 混合架构部署实施细节

考虑到当前的硬件条件（AMD Ryzen 7 PRO 6850H 迷你主机）与云端 API 额度（MiniMax Plus 套餐），本方案将采用**“本地轻算力 + 云端重推理”**的混合计算架构。

### 1. 资源边界与任务分工
* **本地小主机（核心中枢与数据存储）**：
  * **角色**：负责向量化运算（Embedding）、图数据库与向量数据库的本地存储、以及整体数据流的调度。
  * **资源**：充分利用 24GB DDR5 高频内存（8000MHz）极高的带宽优势，快速处理文本块的向量化映射。由于向量模型体积小巧，本地算力充沛，完全不会成为系统瓶颈。
* **云端 MiniMax（重度推理引擎）**：
  * **角色**：承担耗时且极耗显存的知识图谱节点/边缘抽取工作，以及最终问答阶段的长文本复杂推理。
  * **并发**：利用套餐支持的并发能力，多线程异步向云端输送文本块进行处理。

### 2. 本地主机性能优化与分配策略
* **显存分配方案**：建议在 BIOS 中将核显（UMA Frame Buffer Size）专用显存**划拨为 4GB**。
  * **原理**：当前主流的顶级 Embedding 模型体积通常在 2GB 左右，4GB 专用显存完全绰绰有余。保留 20GB 系统内存能够确保图数据库和向量数据库在内存中宽裕运行，避免触发硬盘虚拟内存交换而导致卡顿。同时，Windows 系统在必要时仍会动态调度共享显存，性能释放极佳。
* **本地推理引擎选型**：推荐使用 **Ollama** 等傻瓜式本地大模型运行工具，一键部署并拉取双语向量模型。它能够自动调度 CPU 与 AMD 680M 核显，规避复杂的底层运行库配置，提供极其省心的本地 API 服务。

### 3. 具体实施路径
1. **环境准备**：本地主机一键安装 Ollama 并下载指定的 Embedding 模型；获取云端 MiniMax 的 API Key 与调用凭据。
2. **框架初始化**：基于 Python 与 LightRAG 库，将云端 LLM 接口指向 MiniMax（处理实体抽取与生成），将本地 Embedding 接口指向 Ollama（处理向量映射）。
3. **首次建库运行**：采取无人值守的挂机模式。本地主机会将 155 本（约 153MB）Markdown 文档按块进行向量化，随后在并发限制内持续向云端请求图谱抽取，最后在本地落盘生成图谱数据库。预计耗时在 15-20 小时。
4. **日常检索与增量**：
   * **日常检索**：用户的提问在本地瞬间向量化，穿梭本地图谱获取高低层上下文后，由云端 MiniMax 根据百万级长上下文完成最终解答。
   * **增量追加**：新加入的书籍直接在本地切块并发送云端抽取，新生成的实体和关系将自动合并至原图谱，彻底免除全局重建。
